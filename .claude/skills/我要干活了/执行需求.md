# 执行需求 🔄 (状态机版)

---

## 🔴 铁律（强制遵守）

1. **必须先检查当前状态** - 从断点继续
2. **必须先检查Git状态** - 看已完成多少任务
3. **必须遵守状态机流程** - 不能跳过
4. **必须更新跟踪矩阵和HTML** - 每次变更后

---

## 📍 第一步：检查当前状态

### 1.1 检查状态机状态

```bash
node .claude/skills/我要干活了/scripts/state-manager.cjs get
```

查看 `currentState` 和 `currentRQ`，确认从哪里继续。

---

### 1.2 如果状态是INIT，需要选择需求

如果当前状态是 `INIT`，先查看跟踪矩阵，让用户选择一个需求：

```markdown
## 📋 可选需求列表

| RQ编号 | 名称 | 状态 | 规格 | 计划 |
|--------|------|------|------|------|
| RQ-xxx | xxx | 🚧 规划中 | ❌ | ❌ |
| RQ-yyy | yyy | 📋 规格已完成 | ✅ | ❌ |
| RQ-zzz | zzz | 🔄 计划已生成 | ✅ | ✅ |
```

用户选择需求后，根据当前状态设置状态机：

| 需求状态 | 设置 `currentState` | 设置 `currentRQ` |
|---------|---------------------|-----------------|
| 🚧 规划中 | NEED_BRAINSTORMING | RQ-xxx |
| 📋 规格已完成 | NEED_PLAN | RQ-xxx |
| 🔄 计划已生成 | NEED_BRANCH | RQ-xxx |
| 🔄 执行中 | EXECUTING_TASKS | RQ-xxx |
| ⏳ 等待验证 | WAITING_VALIDATION | RQ-xxx |

---

### 1.3 检查Git历史，确定断点

```bash
# 查看该RQ的所有提交
git log --oneline --grep="RQ-xxx"

# 查看具体提交内容
git show {commit-hash}
```

确定：
- 是否已创建分支
- 已完成多少任务
- 从哪里继续

### 情况B：状态 = NEED_BRAINSTORMING

---

### 情况C：状态 = NEED_PLAN

→ 转到 [新增需求.md](./新增需求.md) 的"阶段3"

---

### 情况D：状态 = NEED_BRANCH

→ 转到 [新增需求.md](./新增需求.md) 的"阶段4"

---

### 情况E：状态 = EXECUTING_TASKS

这是最常见的情况，需要从断点继续执行任务：

**步骤**：
1. 读取计划文档，提取完整任务列表
2. 检查Git历史，确定已完成的任务数（n）
3. 从第 n+1 个任务继续执行
4. **每个任务完成后**：
   - 更新跟踪矩阵：`🔄 {当前}/{总数} 任务完成`
   - 生成HTML
   - Git Commit：`feat({RQ}/T{n}): {描述}`
5. 所有任务完成后，转到 `WAITING_VALIDATION`

---

### 情况F：状态 = WAITING_VALIDATION

→ 转到 [新增需求.md](./新增需求.md) 的"阶段6"

---

### 情况G：状态 = DONE

→ 告诉用户该需求已完成，建议重置状态：
```bash
node .claude/skills/我要干活了/scripts/state-manager.cjs reset
```

## 🔄 断点续执行示例

假设：
- 当前状态：`EXECUTING_TASKS`
- 当前RQ：`RQ-037`
- Git历史显示已完成T1、T2
- 计划中有5个任务

**执行步骤**：
1. 读取计划文档，确认任务3-5的内容
2. 执行任务3
3. 更新跟踪矩阵：`🔄 3/5 任务完成`
4. 生成HTML
5. Git Commit：`feat(RQ-037/T3): xxx`
6. 重复执行任务4、5
7. 所有完成后，转到 `WAITING_VALIDATION`

## ⚠️ 注意事项

1. **不要跳过状态检查** - 总是先看 `state.json`
2. **不要跳过Git检查** - 断点检测很重要
3. **不要强制状态转换** - 必须遵守状态机规则
4. **如果状态混乱** - 可以手动编辑 `state.json` 或重置
