# 执行需求

---

## 💡 选择需求 + 断点检测

请从以下待执行需求中选择。

**选择后，执行断点检测：**

```bash
# 检查该 RQ 的所有 commit
git log --oneline --grep="RQ-xxx"

# 按任务编号精确匹配（优先）
git log --oneline --grep="RQ-xxx/T"
```

1. 读取计划文件，提取总任务数 M
2. 从 git log 提取该 RQ 的 commit 列表：
   - 优先匹配 commit message 中的任务编号（`RQ-xxx/T{n}`）
   - 回退匹配 commit message 与计划任务描述的模糊匹配
3. 向用户报告："检测到 N 个相关 commit，计划文件中有 M 个任务，预计从第 {N+1} 个任务继续"
4. 将断点信息作为上下文传给 subagent-driven-development

## 🔴 七道门控（绝对不可跳过）

### 门控零：禁止直接动手

**如果该需求还没有经过 brainstorming，必须先调用 superpowers:brainstorming，然后走完整流程。**

- 代码已经写好了但没走 brainstorming → ❌ 先补走
- 需求看起来很简单 → ❌ 先走 brainstorming
- 只需要改一行代码 → ❌ 先走 brainstorming

### 门控零点五：新需求识别提醒

**执行过程中，一旦识别到当前需求规格之外的新诉求，必须立即暂停并提醒人类选择归属。**

提醒格式：
> ⚠️ 检测到新需求：「{简要描述}」。当前需求 {RQ-xxx} 尚未完成，请选择：
> 1. 归入当前需求 {RQ-xxx} 的范围
> 2. 新建为独立需求 {RQ-yyy}

- 自行把新功能塞进当前需求 → ❌ 禁止
- 自行开新需求 → ❌ 禁止
- 忽略继续执行 → ❌ 禁止
- 立即提醒人类做决定 → ✅ 唯一正确做法

**实现方式**：调用 subagent-driven-development 时，注入上下文"识别到规格外新诉求 = BLOCKED"，子代理遇到 BLOCKED 状态会暂停报告。

### 门控零点六：修改跟踪矩阵后必须同步 HTML

**每次修改 `项目执行跟踪矩阵.md` 后，必须立即运行：**

```bash
node .claude/skills/我要干活了/scripts/markdown-to-html.js "项目执行跟踪矩阵.md"
```

脚本执行失败 → 报告人类，不得跳过。

### 门控一：每个任务完成后的两阶段审查

**每个任务完成后必须派两个审查子代理，没有任何例外：**

#### 审查一：规格合规审查
- 代码是否实现了规格中描述的所有功能？
- 是否有规格要求但代码遗漏的部分？
- 是否有规格之外的多余实现？
- 组件间数据流是否与规格定义一致？
- 涉及布局变更的任务，子组件是否能在目标容器中完整显示？

#### 审查二：代码质量审查
- 是否存在残留的旧代码？
- 是否有未使用的导入或变量？
- 类型安全是否完整？
- 可测试的逻辑是否有测试覆盖？（TDD 检查）
- 视觉一致性和交互连续性是否保持？

#### 审查规则
1. 规格审查不通过 → 修复 → 重新审查
2. 规格审查通过 → 才进入代码质量审查
3. 代码质量审查不通过 → 修复 → 重新审查
4. 两个审查都通过 → 标记任务完成

#### ⛔ 严禁行为
- 不得跳过任何任务的审查
- 不得以"节省时间"为由省略审查
- 不得仅做 TypeScript 编译检查就替代审查
- 实现子代理必须串行派发，不得并行（避免文件冲突）
- 同一任务的两个审查子代理之间必须串行（规格→质量）

### 门控二：计划阶段的子组件尺寸适配检查

调用 Writing Plans 时必须执行：
1. 涉及布局/容器变更的 task → 计算目标容器实际可用空间
2. 子组件固有尺寸是否超出 → 超出则在计划中写出适配方案
3. 聊天类 UI → scrollToBottom 是默认检查项

### 门控三：需求完成前的人工验证

**所有任务执行完毕、审查通过后，不得直接标记"已完成"。**

1. 启动 dev server
2. 告知用户："需求已实现，请验证以下关键路径："+ 列出 3-5 个
3. **等待用户明确确认"ok"后才更新跟踪矩阵为"已完成"**
4. 用户反馈问题 → 修复 → `git add -A && git commit -m "fix(RQ-xxx): fix validation issues"` → 在时间线追加 `- 🔍 验证发现 N 个问题 → 🔧 已修复` → 生成 HTML → 重新请求验证

**用户确认 ok 后，更新跟踪矩阵三处 + commit：**
- **需求表格**：状态改为 `✅ 已完成`
- **需求总体统计**：已完成+1，进行中-1（或待规划-1）
- **执行时间线**：追加 `- ✅ 完成需求 {RQ-xxx}：{需求名称}`
- **项目状态**：更新"当前状态"和"最后更新"
- **git commit**：`git add 项目执行跟踪矩阵.md 项目执行跟踪矩阵.html && git commit -m "docs(RQ-xxx): complete requirement"`
- 运行脚本生成 HTML

#### ⛔ 严禁行为
- 不得仅凭 TypeScript 编译通过、生产构建成功就标记完成
- 不得自行判断"看起来没问题"就标记完成
- 不得在用户未确认的情况下自动标记完成

### 门控四：Worktree 隔离

**任务执行前必须创建 worktree 隔离开发环境，不得在 main 分支上直接开发。**

1. 调用 `superpowers:using-git-worktrees` 创建工作树
2. 在工作树中执行所有任务
3. 完成后通过 `superpowers:finishing-a-development-branch` 合并回主分支

**豁免**：人类明确声明在 main 上直接开发时，可跳过此门控，但必须在跟踪矩阵备注中记录。

## 🎯 执行策略（唯一路径）

1. **断点检测**：`git log --grep="RQ-xxx"` 检测已完成任务，优先匹配任务编号 `RQ-xxx/T{n}`，确定续执行起点
2. **文档检查**：缺少规格 → 补走 brainstorming + 手动接管 + commit；缺少计划 → 补走 writing-plans + 手动接管 + commit
3. **需求规格** - 调用 superpowers:brainstorming → **手动接管** → 更新跟踪矩阵 + commit 规格文件
4. **执行计划** - 调用 superpowers:writing-plans（跳过执行方式选择）→ **手动接管** → 更新跟踪矩阵 + commit 计划文件
5. **Worktree** - 调用 superpowers:using-git-worktrees 创建隔离环境
6. **任务执行** - 调用 superpowers:subagent-driven-development（⛔ 固定使用，含门控一）
   - 注入上下文：识别到规格外新诉求 = BLOCKED
   - 注入上下文：commit message 格式 `feat(RQ-xxx/T{n}): {描述}`
   - 实现子代理串行派发
   - 每个任务完成后：需求表格状态更新为 `🔄 N/M 任务完成`，生成 HTML
7. **完成处理** - 调用 superpowers:finishing-branch（合并回 main + 清理 worktree）
8. **人工验证** - 启动 dev server，引导用户验证（门控三）
9. **标记完成** - 用户确认 ok 后更新跟踪矩阵（表格+统计+时间线+项目状态）+ commit

### 执行细节
- 固定使用 subagent-driven-development，不提供 Inline Execution 选项
- 实现子代理串行派发，审查子代理串行执行（规格→质量）
- 自适应模型选择：Haiku（简单）→ Sonnet（标准）→ Opus（复杂），不影响门控要求
- 需求变更：小变更直接调整 + 时间线记录，大变更回 brainstorming 更新规格

| 阶段 | 技能名称 | 功能 |
|------|---------|------|
| 需求规格 | superpowers:brainstorming | 生成需求规格设计文档 |

| 任务执行 | superpowers:subagent-driven-development | 代理驱动执行 + 两阶段审查 |
| 完成分支 | superpowers:finishing-a-development-branch | 构建验证和收尾 |
