## ⛔ 铁律

### 铁律一：禁止直接动手

**必须先完成需求编号分配 + 跟踪矩阵登记，然后调用 superpowers:brainstorming，没有任何例外。**

### 铁律二：新需求识别必须提醒人类

**当存在未完成的需求时，识别到新诉求 → 立即暂停提醒人类选择归属。**

### 铁律三：修改跟踪矩阵后必须同步 HTML

**每次修改 `项目执行跟踪矩阵.md` 后，必须立即运行：**

```bash
node .claude/skills/我要干活了/scripts/markdown-to-html.js "项目执行跟踪矩阵.md"
```

脚本执行失败 → 报告人类，不得跳过。

### 铁律四：Superpowers 技能转场必须手动接管

**brainstorming 完成后不会暂停——必须手动接管：更新跟踪矩阵 + commit spec，再调用 writing-plans。writing-plans 完成后同理：更新跟踪矩阵 + commit plan，再调用 subagent-driven-development。**

## 🍎 乔布斯设计理念约束（界面/功能需求必遵）

> ⚠️ 此约束在 brainstorming 和 writing-plans 阶段即生效，必须提前阅读。

### 1. 极简（Simplicity）
- 首屏即核心：用户打开界面立刻知道该做什么
- 消除冗余：同类信息只保留一个展示入口
- 配置收拢：非核心配置放入可折叠区域

### 2. 专注（Focus）
- 一次一个主任务：首屏只有一个核心 CTA
- 降噪：删除装饰性元素
- 预设档位优于连续滑块

### 3. 直觉（Intuition）
- 零说明书：界面自解释
- 最短路径：操作步骤数最小化
- 状态连续：页面切换不丢失用户输入

### 4. 一致性（Consistency）
- 统一视觉语言：颜色、字体、间距、圆角用 CSS 变量管理
- 交互模式一致：同类操作用同样控件

### 5. 工匠精神（Craftsmanship）
- 像素级精确：间距对齐、颜色统一、动画流畅
- 无残留：删除旧组件后清理所有引用
- 无半成品：每个交付组件完整可用

### 执行要求
- **Brainstorming 阶段**：规格文档必须包含"设计理念合规检查"章节
- **Writing Plans 阶段**：涉及布局变更的 task 必须检查子组件尺寸适配，聊天类 UI 必须包含 scrollToBottom
- **Executing Plans 阶段**：代码质量审查必须检查残留旧代码、视觉一致性、交互连续性

## 📋 执行步骤（严格按序）

### ✅ 步骤一：分配编号 + 更新跟踪矩阵（⛔ 绝对首步）

1. 查看项目跟踪矩阵，自动递增编号（如 RQ-020 → RQ-021）
2. 字段默认值填充：描述=名称，优先级=高，周期=1天
3. **更新跟踪矩阵三处**：
   - **需求表格**：新增一行，规格文件列填 `—`，计划文件列填 `—`，状态 `🚧 规划中`
   - **需求总体统计**：总数+1，待规划+1
   - **执行时间线**：当日追加 `- 🆕 新增需求 {RQ-xxx}：{需求名称}`（如当日无标题则先加 `### YYYY-MM-DD`）
4. 运行脚本生成 HTML

### ✅ 步骤二：调用 superpowers:brainstorming

1. 调用 `Skill` 工具，参数 `skill: "superpowers:brainstorming"`
2. brainstorming 会生成规格文档，保存到 `docs/superpowers/specs/`
3. **⚠️ brainstorming 完成后可能自动调用 writing-plans——必须拦截，手动接管**

### ✅ 步骤三：手动接管——回写跟踪矩阵 + commit 规格文件

brainstorming 完成后，**不跟着自动转场**，手动执行：
- **需求表格**：规格文件列填入内联链接
- **执行时间线**：追加 `- 📋 生成规格：{RQ-xxx}`
- **git commit**：`git add docs/superpowers/specs/{文件} 项目执行跟踪矩阵.md 项目执行跟踪矩阵.html && git commit -m "docs(RQ-xxx): add spec"`
- 运行脚本生成 HTML

### ✅ 步骤四：调用 superpowers:writing-plans

1. 调用 `Skill` 工具，参数 `skill: "superpowers:writing-plans"`
2. writing-plans 会生成实现计划，保存到 `docs/superpowers/plans/`
3. **⚠️ writing-plans 完成后会 offer 执行方式选择——固定选择 subagent-driven-development，跳过选择环节**

### ✅ 步骤五：手动接管——回写跟踪矩阵 + commit 计划文件

writing-plans 完成后，手动执行：
- **需求表格**：计划文件列填入内联链接，状态改为 `🔄 计划已生成`
- **执行时间线**：追加 `- 📝 生成计划：{RQ-xxx}`
- **git commit**：`git add docs/superpowers/plans/{文件} 项目执行跟踪矩阵.md 项目执行跟踪矩阵.html && git commit -m "docs(RQ-xxx): add plan"`
- 运行脚本生成 HTML

### ✅ 步骤六：创建 worktree + 调用 superpowers:subagent-driven-development

1. 调用 `superpowers:using-git-worktrees` 创建隔离工作树（门控四）
2. 调用 `superpowers:subagent-driven-development`，**注入额外上下文**：
   - "识别到规格外的新诉求 = BLOCKED，立即暂停报告控制器"（门控零点五）
   - "commit message 格式：`feat(RQ-xxx/T{n}): {描述}`，便于断点检测"
3. 实现子代理**串行派发**（不得并行），审查子代理串行执行（规格→质量）
4. 每个任务审查通过后、派发下一个任务前，controller 必须更新需求表格状态列：`🔄 N/M 任务完成`（N=已完成数，M=总任务数），然后生成 HTML

### ✅ 步骤七：调用 superpowers:finishing-branch

1. 构建验证
2. 合并回主分支 + 清理 worktree

### ✅ 步骤八：人工验证

启动 dev server，列出 3-5 个核心交互路径让用户验证。

**用户确认 ok 后：**
- **需求表格**：状态改为 `✅ 已完成`
- **需求总体统计**：已完成+1，待规划-1（或进行中-1）
- **执行时间线**：追加 `- ✅ 完成需求 {RQ-xxx}：{需求名称}`
- **项目状态**：更新"当前状态"和"最后更新"
- **git commit**：`git add 项目执行跟踪矩阵.md 项目执行跟踪矩阵.html && git commit -m "docs(RQ-xxx): complete requirement"`
- 运行脚本生成 HTML

**用户反馈问题时：**
- 修复问题后，在执行时间线追加：`- 🔍 验证发现 N 个问题 → 🔧 已修复`
- **git commit**：`git add -A && git commit -m "fix(RQ-xxx): fix validation issues"`
- 运行脚本生成 HTML
- 再次请求用户验证，直到用户确认 ok
