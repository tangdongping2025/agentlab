# 我要干活了！

---

## 🚀 核心功能

1. 📋 **新增需求** — 分配编号 → 头脑风暴 → 规格设计 → 计划制定 → 任务执行 → 人工验证
2. 🔄 **执行需求** — 从已有需求继续执行，完整流程 + 七道门控
3. 📊 **查看项目状态** — 项目整体进度和需求状态

---

## 🔴 铁律（最高优先级）

### ⛔ 铁律一：禁止直接动手

**新增需求时，不管需求简单、复杂、还是看起来很直接，都绝对不允许直接动手实现。必须先完成需求编号分配 + 跟踪矩阵登记，然后调用 brainstorming 技能，没有任何例外。**

- "这个很简单" → ❌ 不能跳过
- "需求很明确了" → ❌ 不能跳过
- "只是改个文字/颜色" → ❌ 不能跳过
- "用户已经说得很清楚了" → ❌ 不能跳过

原因：简单需求跳过头脑风暴会导致理解偏差、遗漏边界情况、返工浪费。

### ⛔ 铁律二：新需求识别必须提醒人类

**当存在未完成的需求时，一旦在对话中识别到新的功能/优化诉求，必须立即暂停并提醒人类选择归属，不能自行决定。**

提醒格式：
> ⚠️ 检测到新需求：「{简要描述}」。当前需求 {RQ-xxx} 尚未完成，请选择：
> 1. 归入当前需求 {RQ-xxx} 的范围
> 2. 新建为独立需求 {RQ-yyy}

- 自行把新功能塞进当前需求 → ❌ 禁止
- 自行开新需求 → ❌ 禁止
- 忽略新诉求继续执行 → ❌ 禁止
- 立即提醒人类做决定 → ✅ 唯一正确做法

### ⛔ 铁律三：修改跟踪矩阵后必须同步 HTML

**每次修改 `项目执行跟踪矩阵.md` 后，必须立即运行脚本重新生成 `项目执行跟踪矩阵.html`，没有任何例外。**

```bash
node .claude/skills/我要干活了/scripts/markdown-to-html.js "项目执行跟踪矩阵.md"
```

- 修改 MD 后忘了生成 HTML → ❌ 禁止
- 用 Edit 工具直接改 MD 而不跑脚本 → ❌ 禁止
- 脚本执行失败 → ❌ 不得跳过，必须报告人类
- 改完 MD 立刻跑脚本生成 HTML → ✅ 唯一正确做法

原因：MD 和 HTML 是同一份数据的两个视图，不一致会导致人类查看 HTML 时看到过时信息。

### ⛔ 铁律四：更新跟踪矩阵必须三处同步

**每次更新跟踪矩阵时，必须同时更新三处：**

1. **需求表格** — 新增行、更新列、改状态
2. **需求总体统计** — 总数、已完成、进行中、暂停、待规划
3. **执行时间线** — 追加 🆕/📋/📝/✅/🔍→🔧 记录

- 只改表格忘了统计和时间线 → ❌ 禁止
- 三处都改 + 生成 HTML → ✅ 唯一正确做法

### ⛔ 铁律五：关键文档产出后必须 git commit

**规格文件、计划文件生成后，必须立即 git commit。** 任务代码由子代理自动 commit，无需额外操作。

| 产出 | commit message 格式 |
|------|-------------------|
| 规格文件 | `docs(RQ-xxx): add spec` |
| 计划文件 | `docs(RQ-xxx): add plan` |
| 验证修复 | `fix(RQ-xxx): fix validation issues` |
| 需求完成 | `docs(RQ-xxx): complete requirement` |

- 生成规格/计划后忘了 commit → ❌ 禁止
- 人工验证修复后忘了 commit → ❌ 禁止
- 产出后立即 commit → ✅ 唯一正确做法

原因：规格和计划是真实工作产出，不 commit 则会话中断后丢失，且 git log 是续执行断点检测的数据源。

### ⛔ 铁律六：Superpowers 技能转场必须手动接管

**每次调用 superpowers 技能（brainstorming、writing-plans 等）完成后，必须手动接管——更新跟踪矩阵 + git commit——再调用下一个技能。不得依赖技能的自动转场。**

- brainstorming 完成后自动调用 writing-plans → ❌ 必须先手动更新跟踪矩阵 + commit spec
- writing-plans 完成后展示执行方式选择 → ❌ 固定使用 subagent-driven-development，跳过选择
- 依赖技能的自动转场继续 → ❌ 禁止
- 技能完成后手动接管、更新矩阵、commit、再调下一个 → ✅ 唯一正确做法

原因：superpowers 技能不知道跟踪矩阵的存在，自动转场会跳过矩阵更新和 commit 步骤。

### ⛔ 铁律七：需求变更必须报备

**执行过程中，若人类要求修改已批准的规格（非新需求，而是原需求的调整），必须走变更流程，不得自行修改。**

- **小变更**（不影响计划和架构）：直接调整 + 时间线记录 `- 🔄 变更(RQ-xxx): {简要描述}`
- **大变更**（影响计划结构或架构）：回到 brainstorming 更新规格 → 更新计划 → 更新跟踪矩阵 + commit

- 自行修改规格不留记录 → ❌ 禁止
- 任何变更都不记录 → ❌ 禁止
- 按大小走变更流程 + 记录 → ✅ 唯一正确做法

## 🎯 完整流程（唯一路径）

### 1. 新增需求阶段

1. 填写需求信息（描述默认=名称，优先级默认=高，周期默认=1天）
2. **分配需求编号 + 更新跟踪矩阵三处**（⛔ 绝对首步，先于一切）
3. 调用 brainstorming → **手动接管** → 更新跟踪矩阵 + commit spec
4. 调用 writing-plans（跳过执行方式选择，固定 subagent） → **手动接管** → 更新跟踪矩阵 + commit plan
5. 创建 worktree 隔离开发环境（门控四）→ 调用 subagent-driven-development（含门控一：串行实现、两阶段审查）
   - 每个任务完成后更新进度 `🔄 N/M` + 生成 HTML
   - 注入上下文：识别到规格外新诉求 = BLOCKED（门控零点五）
6. 调用 finishing-branch → 合并回主分支 + 清理 worktree
7. 人工验证 → 用户反馈问题则记录 🔍→🔧 + commit → 用户确认 ok → 更新跟踪矩阵三处 + commit

### 2. 执行需求阶段

- **断点检测**：`git log --grep="RQ-xxx"` 确定已完成任务数，优先匹配任务编号 `RQ-xxx/T{n}`
- 检查需求状态：缺少规格 → 补走 brainstorming + 手动接管；缺少计划 → 补走 writing-plans + 手动接管
- 创建/复用 worktree → 从断点继续执行，同样经过七道门控

## 🔴 七道门控（绝对不可跳过）

| 门控 | 阶段 | 内容 |
|------|------|------|
| 门控零 | 需求开始 | 禁止直接动手，必须先走 brainstorming |
| 门控零点五 | 执行过程中 | 识别到新需求 → BLOCKED，暂停提醒人类选择归属 |
| 门控零点六 | 修改跟踪矩阵后 | 必须运行脚本重新生成 HTML，失败则报告人类 |
| 门控一 | 每个任务完成后 | 两阶段审查：规格合规 + 代码质量（含测试覆盖检查），实现子代理串行派发 |
| 门控二 | 计划制定时 | 子组件尺寸适配检查 |
| 门控三 | 需求完成前 | 人工验证，用户确认 ok 后才标记完成 |
| 门控四 | 任务执行前 | Worktree 隔离，不在 main 分支上直接开发 |

## 🛡️ 豁免机制

**人类在需求编号分配时，可以声明豁免特定步骤：**

| 豁免类型 | 适用场景 | 豁免后流程 |
|---------|---------|-----------|
| 跳过 brainstorming | 极简改动（改颜色、改文字） | 直接写计划 + 执行 |
| 跳过 writing-plans | 单一文件小修改 | brainstorming 后直接执行 |
| 跳过 worktree | 紧急修复 | 在 main 上直接开发 |

**豁免规则：**
- 必须由人类明确声明，AI 不得自行决定豁免
- 豁免必须在跟踪矩阵备注中记录
- 门控三（人工验证）永远不可豁免

## 🤖 自适应模型选择

- **Haiku**（简单任务）：修复bug、小型优化、工具函数
- **Sonnet**（标准任务）：组件开发、功能实现、界面设计
- **Opus**（复杂任务）：架构设计、系统重构、复杂问题解决

模型选择只影响效率，不影响质量——无论用哪个模型，七道门控都必须通过。
